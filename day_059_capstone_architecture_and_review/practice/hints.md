# Day 059 hints: Capstone architecture and review

Use these after attempting the the numbered exercises in this lesson. They are specific to **Capstone architecture and review** and should unblock the next thought without replacing it.

## Hints

1. Begin with the learner problem: A project is not finished when the happy path works; other people need to understand its architecture, evidence, limitations, and recovery plan.
2. Run the smallest example unchanged and inspect the evidence for a portfolio-ready local case-management feature with architecture and evidence notes.
3. Trace the input, operation, output, and owner at demo evidence versus production claims, operational ownership, and residual risk.
4. Change exactly one input related to How do we design a real app?; keep the rule fixed.
5. For Where do routes, components, data, and policies live?, decide the normal and boundary behavior before coding.
6. Reproduce the likely mistake: Confuse a clean build or screenshot with proof that every user, permission, failure, and deployment condition is safe.
7. Repair the smallest line or boundary; do not hide the failure with a broad workaround.
8. Keep the data local and synthetic while you test How do we document trade-offs?.
9. Assert a visible result or public contract rather than a private implementation detail.
10. Use the same fixture to apply capstone architecture and review to a portfolio-ready local case-management feature with architecture and evidence notes.
11. A passing build proves only the checked build completed; record what remains untested.
12. Your review note should name the owner, evidence, limitation, and boundary: demo evidence versus production claims, operational ownership, and residual risk.
